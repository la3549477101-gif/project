## 二、已经完成的功能

### 1. 客户与项目

- 按采购公司集中查看项目，区分实际采购公司与最终使用产品的终端客户。
- 客户档案、备案资料、长期交易/付款/对账/开票条件；不确定信息可留空。
- 新建客户成功后在桌面创建对应文件夹，失败提示并可重试，已有文件保留。
- 一个项目下维护多个材料型号和成品规格；业务交易阶段与EVT/DVT/PVT测试阶段分开。
- 项目及规格跟进历史、字段变化、下一步和下次跟进日期；明细归档/恢复及项目删除保护。
- 本周更新包括新增及实际修改；重点项目单独标记，支持公司筛选。

### 2. 报告主表与界面

- 原项目报告18个业务字段统一展示与集中编辑，兼容旧九字段及原报告元数据。
- 采购公司、项目名称、终端客户三列固定，可通过信息栏抽屉一起收起/展开。
- 每行“编辑”位于勾选框下方并固定；金额定位按钮直接跳到报价和年需求预测。
- 水下浅蓝透光风格、半透明面板、分界线；后续页面继续沿用。
- 品牌为独立字段；负责人、品牌、产品线、币种、数量单位、计价说明支持默认填入。
- 默认项初始关闭，用户自行启用、修改或停用；只对新建报告预填，当次可改或清空，不回填旧资料。独立新增规格入口目前仍手填。

### 3. 订单和金额

- 样品、量产及复购分别建独立订单，一单可有同项目多个规格明细。
- 含税单价；数量乘单价逐行四舍五入2位后合计，客户累计按币种分开。
- 先预览再确认，保存下单时客户条款和规格快照，防止重复提交。
- 订单只读详情、客户累计金额及订单CSV导出。
- 报价、预估年营业额、实际订单金额分别记录；订单累计不代表已交货或已收款。

### 4. 导入、导出与稳定运行

- CSV/XLS/XLSX预览、工作表选择、逐行校验、勾选确认；完全相同记录跳过，其他变化新增，不自动覆盖。
- 四工作表Excel导出：开发、成交、EOL、重点项目，原18列顺序保留；有品牌时末尾追加品牌列。
- 导出涵盖全部客户当前报告行，不随界面筛选缩小；重点表为重复视图，不能跨四表重复累计。
- 日常前端使用静态构建，后端及前端从独立快照运行；三服务健康检查、重复启动互斥、部分失败恢复及一次旧健康版本回退。
- 原桌面快捷方式继续使用；start-app.cmd启动，check-app.cmd检查，repair-app.cmd重启，stop-app.cmd停止。

## 四、如何上传到GitHub

### 建议本次上传的内容

上传现有开发成果和这份接续文档到原仓库project。目标远程origin、目标分支main，保持Public；保留codex/report-ledger本地开发分支。核对远程没有额外提交时采用普通推送，不强制覆盖历史。此次只同步源码和文档，暂不创建新版本号或安装包。

若确认时远程main已有其他人新增提交，先拉取并处理差异，不能直接覆盖。

### 执行步骤

1. 保存文档并作本地Git提交。
2. 确认仓库project、Public、origin/main及本次公开的源码/脱敏文档范围。
3. 检查待上传提交没有真实业务数据库、客户文档、密钥、日志或本地备份。
4. 更新远程状态，确认可以正常推送后上传。
5. 核对远程main提交编号和接续文档可见，再记录上传结果。

开发者可在仓库根目录执行以下命令；推送行须在用户确认后执行：

```powershell
git status --short
git fetch origin
git log origin/main..HEAD --oneline
git push origin HEAD:main
```

不需要重新创建仓库或上传整个桌面文件夹。上传源码不需要停止正在运行的应用。

### 业务数据如何保留

当前真实数据在本地H2数据库，桌面客户文件夹单独保存。换电脑时应先正常停止应用，再备份整个backend/springboot/data和客户文件夹，另外安全转移；不能上传公开GitHub。数据库里的默认值也随数据库备份迁移。

## 五、后续开发计划

以下是基于当前进度的建议顺序，不表示这些功能已经完成；不在本次保存文档时直接开发。

| 优先级/阶段 | 目标 | 主要交付 | 完成标准 |
| --- | --- | --- | --- |
| P0 交接与补验 | 保存和同步当前成果，减少后续重复开发 | 本接续文档、源码上传、获得浏览器授权后的未完成复验 | 远程版本可追溯；抽屉记忆、默认清空、品牌实际下载逐项记录结果 |
| P1 交货登记 | 让订单能记录实际交付 | 整单交完快捷登记、按订单明细分批交货、交货日期/数量/备注及历史 | 已交/未交数量准确；禁止超交；重复提交不重复登记；不自动标记收款 |
| P2 实际收款 | 区分订单总额、已收和未收 | 一次收清入口、收款日期/金额、客户分币种应收/已收/未收，沿用既定条款 | 保存订单不等于收款；不混币种；异常金额明确处理；交货与收款独立 |
| P3 数据保护与迁移 | 正式业务增长前补可靠备份恢复 | 应用内备份/恢复指引或入口、附件与客户目录关联、跨电脑迁移说明 | 使用测试备份完成恢复演练；不覆盖未知文件；失败保留原数据并能恢复 |
| P4 Word客户文件 | 新客户资料填写一次，按空白模板生成文档 | 清理模板、字段映射、缺失/不确定项清单、自检、保存到客户桌面目录及版本归档 | 不复制样例客户信息；原模板和旧文件保留；人工审批不默认通过；版式与模板核对 |
| P5 导入更新 | 持续更新现有项目时减少重复 | 客户/项目/规格匹配候选、逐字段差异预览、人工确认新增或更新、原文件来源 | 重复文件不重复建项目；无明确依据不合并；旧九字段和原资料可追溯 |
| P6 截图草稿与AI | 从聊天截图提取后核对写入 | 统一录入草稿、来源/空缺/冲突提示、默认值合并、确认后新增或更新；之后接视觉API与密钥设置 | 不把意向当正式订单；不确定留空；确认前零业务写入；失败仍可手填 |

建议下一项从P1交货登记开始，沿用用户已确认的“大多数整单交完，偶尔分批”规则。P2先覆盖通常一次收清的常规情况；分次、跨订单收款、退款等在影响数据关系前逐项确认，不能擅自简化或默认纳入。

AI阶段可让模型只输出变化字段，在本机补负责人/品牌等默认值，再让用户核对；减少重复文字传输与输出，不保证截图token或总费用按固定比例下降。
