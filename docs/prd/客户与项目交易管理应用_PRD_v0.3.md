# 客户与项目交易管理应用产品需求文档

版本：v0.3  
整理日期：2026年10月23日（北京时间）  
状态：需求梳理稿，供后续设计和开发使用  
适用对象：用户、后续开发与维护人员

## 1 文档目的和当前结论

将现有的 ODM 项目登记工具扩展为本机使用的客户档案、项目跟进及订单管理应用。用户获得新客户时建立独立客户档案；所有客户的项目统一管理；同一项目内按材料型号和成品规格分别跟进业务进度；每笔样品订单、量产订单和后续采购独立记录，并保留交货与收款情况。

用户主要提供聊天截图，由对话中的 AI 助手识别资料、检查并通过应用录入。应用后续可以接入视觉模型 API，让用户直接在应用中上传截图识别。AI 应先生成可核对的录入草稿，不确定的字段留空，询问用户并由用户补填。

客户资料备案表需要按用户提供的空白 Word 模板填写。AI 填入有依据的内容后再检查一遍；不确定项留空交给用户补填；输出文件归档到桌面对应客户文件夹。

本PRD包含两组Word模板与已填样例的对照结论，字段填写规则见同目录《客户表单填写区域与规则_v0.1.md》。客户桌面文件夹的创建时点已明确为在软件中成功新建客户时，无需等待Word文件生成。资信模板已收到，但存在客户相关预填内容，正式用于新客户前需准备经确认的清理副本。

本 PRD 记录的是建设需求，具体实现进度以《开发进度与后续计划》为准。2026-10-26已实现客户档案及备案/交易条件、项目归属、桌面客户目录、字段变更历史、本周更新、项目型号规格及独立业务阶段和跟进记录；完整项目明细报告导入导出、订单、交货、收款、截图识别和Word自动填写仍待建设。新增功能的实施不代表本文全部业务场景已完成验收。

### 1.1 要求的状态

- **已确认**：用户在对话中明确确认的业务要求，后续开发应遵守。
- **设计建议**：为落实已确认要求提出的实现或交互方案，可在详细设计时调整。
- **待确认**：尚未取得明确答案的事项，不得当作已同意的业务规则。

### 1.2 当前交付范围

本次只整理 PRD，暂停继续逐项询问需求。没有因本次整理而修改应用业务代码或用户原始工作表。后续开发前按本文的待确认清单继续沟通，问题一次询问一个。

## 2 业务背景与参考资料

### 2.1 工作方式

1. 获得新客户，收集客户资料，建立该客户独立档案，确定长期交易和收款条件。
2. 填写客户备案表，按需要收集资信资料及相关证明文件。
3. 将新项目加入所有客户共用的项目台账。
4. 持续记录报价、送样、验证、待下单、正式下单等业务进度。
5. 同一客户后续采购时复用原客户档案；同一项目新增订单时保留原项目和历史订单；新项目建立新项目记录。
6. 按需导出公司的项目开发报告及客户备案文件。

### 2.3 参考报告的观察和限制

- 参考报告“开发”表第81至82行写有已下样品单，第112至114行写有下样品单，仍归在开发表。因此，样品订单实际成交与项目是否进入量产是两个独立事实。
- “开发”表第46至49行写有已下备料单，表明出现下单字样也不能直接自动判定项目已经量产。
- 参考报告“成交”表仅有表头，没有可验证的成交样例。正式量产下单后归入成交属于后续与用户确认采用的默认规则，并非仅凭该文件完整推导出的公司制度。
- 同一客户、同一项目有多个材料型号；相同材料型号还可出现不同成品规格。报告的一行不能简单等同于一个独立项目或一笔订单。
- 预计量产时间既有日期，也有“2026年Q4”等季度文本。后续导入和导出应保留日期精度，不能强行转换成某一天。

## 3 已确认的关键业务规则

| 编号 | 已确认规则 |
| --- | --- |
| BR-01 | 每个客户建立独立档案，所有客户的项目汇总在统一项目台账。 |
| BR-02 | 客户指实际向用户公司采购、下单和付款的企业；终端客户指最终使用整体产品的企业。 |
| BR-03 | 示例：英维克采购并组装后交付谷歌，客户为英维克，终端客户为谷歌。 |
| BR-04 | 同一实际项目保留一个项目档案；项目下保留全部跟进历史及多笔订单。 |
| BR-05 | 同一项目下不同材料型号、不同成品规格需要分别报价、分别跟进交易阶段。 |
| BR-06 | 跟进的重点是与对方公司的交易推进阶段。EVT、DVT、PVT等测试阶段属于辅助信息。 |
| BR-07 | 一个型号可能已经正式下单，另一个型号仍在报价，不能用项目的单一状态覆盖所有明细。 |
| BR-08 | 每笔样品单也是一笔真实订单；验证通过后的量产单是另一笔订单；之后采购继续新增订单。 |
| BR-09 | 每笔订单都需要跟进交货和收款情况。 |
| BR-10 | 一张订单可以同时包含多个材料型号或成品规格。 |
| BR-11 | 大多数订单整单交货、一次收清货款；实际存在分批交货，需要保留多次交货记录。 |
| BR-12 | 交易方式、收款条件等通常在首次客户建档时确定，后续交易沿用客户档案，不要求每笔订单重复选择。 |
| BR-13 | “重点项目”是独立标记，可以同时属于开发或成交，不是互斥的项目生命周期状态。 |
| BR-14 | 报告默认将样品、测试及备料阶段归开发；确认正式量产下单后归成交，保留手动调整入口。 |
| BR-15 | 同一项目内已量产和仍在开发的不同明细要保留各自交易阶段。 |
| BR-16 | AI截图录入先由当前对话中的助手识别并操作应用，后续再考虑接入应用内AI API。 |
| BR-17 | 客户备案表由AI识别填写后再自检；不确定项留空并询问用户，由用户手动补填；文件放入桌面对应客户文件夹。 |
| BR-18 | 需求沟通一次只询问一个问题。 |
| BR-19 | 在软件中成功新建客户时，自动在桌面创建该客户文件夹并关联客户档案，不等到导出或生成Word时才创建。 |

“各明细分别归入开发或成交表”是依据BR-15提出的导出设计建议；最终分表效果需要在导出样例中核对。

## 4 产品目标与范围

### 4.1 产品目标

- 客户基本资料和交易条件复用，减少客户档案重复建立与重复录入。
- 统一查看客户、项目及每种型号规格的最新业务进度，同时能查看历史。
- 清楚区分预计需求、实际订单、已交货数量和实际收款，避免相互覆盖或混加。
- 支持从截图提取资料，经过检查、补填和确认后写入正式记录。
- 按原有工作模板输出客户备案表和项目报告。
- 保持当前本机运行方式和用户已经选择的技术框架。

### 4.2 计划模块

1. 客户档案与客户文档归档。
2. 统一项目台账和型号规格明细。
3. 业务跟进历史。
4. 订单及多项订单明细。
5. 交货与收款记录。
6. 截图资料和待确认录入草稿。
7. 项目报告、客户Word文件及数据备份导出。

### 4.3 当前不直接承诺的范围

以下事项尚未获得完整需求，不纳入已经确认的首期功能承诺：完整财务记账、税务申报、银行自动对账、ERP集成、库存与生产排程、多人审批系统、云端部署及跨设备同步。

客户资信调查表的全字段应用内填写和自动生成尚未确认；不能将客户备案表自动填写的确认扩大解释为全部资信财务字段也要结构化入库。

## 5 记录关系与业务粒度

### 5.1 核心关系

```text
客户档案
├─ 客户备案表、资信资料、证明文件
├─ 项目 A
│  ├─ 型号甲 + 规格1：报价、需求预测、交易阶段、跟进历史
│  ├─ 型号甲 + 规格2：独立报价、独立交易阶段
│  └─ 型号乙 + 规格1：独立报价、独立交易阶段
└─ 项目 B

客户订单 001（样品）
├─ 明细1：关联项目和具体型号规格
└─ 明细2：关联项目和具体型号规格

客户订单 002（量产）
├─ 多条订单明细
├─ 一次或多次交货记录
└─ 实际收款记录
```

客户、项目、型号规格明细和订单均使用稳定的内部编号建立关联，不以客户简称、项目名称或材料型号作为唯一标识。

### 5.2 关键区分

- 项目主档用于描述整体项目和汇总查看。详细业务阶段、价格及规格保存在项目明细。
- 项目报告按“客户＋项目＋型号＋规格”的明细层级展示最新情况，不按每笔订单复制整个项目及预测需求。
- 订单用于描述每笔真实采购，订单明细记录本次采购的具体项目产品、数量和成交价格。
- 同一型号规格可以被多笔订单引用；新订单不会删除旧订单，也不会把原项目视为一个新项目。
- 业务跟进记录描述发生了什么以及何时发生；已保存历史与当前状态分开保留。
- 预计年用量、项目预计总需求、测试需求、订单数量、交货数量分别存储，不相互覆盖。

## 6 客户档案需求

### 6.1 客户资料

FR-C01 新建客户档案，记录实际交易客户。支持客户全称和常用简称，避免同一企业因简称不同被重复创建。

FR-C02 客户基本信息和长期交易条件按空白客户备案模板组织。初次建档填写，后续项目与订单引用客户档案。

| 字段组 | 模板字段 |
| --- | --- |
| 建档信息 | 我司交易抬头、建档类型、变更内容、客户名称、所属行业 |
| 联系资料 | 地址、电话、传真、联系人、邮箱、手机号 |
| 需求概况 | 需求产品、客户月用量 |
| 长期交易条件 | 交易方式、收款条件、信用额度、其他说明 |
| 对账开票 | 对账周期、对账日期、开票日期、是否含税 |
| 档案与评估 | 法人身份证复印件情况、营业执照复印件情况、正式合同情况、客户等级、客户类型 |
| 经办审核 | 业务员及日期、审批及日期、核准及日期 |

FR-C03 收款条件保留模板中的预付款、货到付款、月结30/60/90/120/150/180天等选项，并支持真实约定的补充说明。审批、核准、资信结论不能由AI推测或代为作出。

FR-C04 后续订单沿用客户确定的交易条件。用户正式变更客户条款时保留变更记录；设计上应保留历史订单当时适用条款，避免旧订单被最新条款追溯改变。该历史快照属于设计建议，具体展示方式待详细设计。

FR-C05 支持进入客户档案查看该客户全部项目、订单和归档文档。客户档案与终端客户信息分开，不能将谷歌等终端企业误建为实际付款客户。

### 6.2 Word备案表填写与检查

FR-C06 以用户提供的空白Word备案模板为格式依据，根据识别得到且有依据的客户资料填写对应字段。

FR-C07 填写后由助手自检，至少核对客户主体、字段对应关系、来源、金额与单位、联系方式、付款条件以及未填项。格式正确不等于事实正确，自检必须结合原始资料。

FR-C08 不确定、未提供或存在冲突的字段保持空白，列出问题交给用户补填。不得通过客户名称推断付款条件、信用额度、身份证信息、营业执照情况、审批结果等。

FR-C09 对用户一次只提出一个问题。用户可补充资料或选择手动填写。手动填写在应用中进行还是直接编辑导出的Word，入口尚待确认；两者的数据回写方式必须明确。

FR-C10 输出到桌面对应客户文件夹。使用已有客户文件夹前核对主体；新客户需要创建对应目录。保留空白模板原件，已填档案按版本保存，不自动覆盖旧版本。

FR-C11 空白项未补完时是否允许输出标记为待补全的草稿，以及文件名、子目录结构等，属于待确认的归档细节。

FR-C12 原模板为旧版`.doc`。实现前需要确定保留`.doc`还是生成经过版式核对的`.docx`；不可在没有检查的情况下声称转换后完全保留格式。

### 6.3 资信调查与附件

FR-C13 客户档案需要能关联对应的资信调查文件及其他客户证明材料。原文件和新生成文件要有清楚的客户归属。

资信调查空白模板已收到并完成正文字段对照。是否全字段入库、是否自动生成资信表仍待确认。模板中预留的法人代表、开户银行、账号、填表人、经营评价及资料来源不能成为新客户默认值，具体映射见填写规则附件。

FR-C14 新客户文件生成前，对选用模板检查客户相关预填值；准备经确认的清理副本，保留用户原模板。固定标签、输入字段、公司配置、评估审批项和样例空白字段分别处理，不通过模板与样例文本相同就认定为固定文字。

FR-C15 样例空白不等于正式免填；跨表或同表识别号码不一致、地址类型不同、注册资本主体不同等情况要留空或提示核对，不自动猜测修正。自动填写只以当前客户有依据的资料为准。

### 6.4 新建客户与桌面文件夹

FR-C16 在软件中提交并成功建立客户档案时，自动在当前Windows用户的桌面创建对应客户文件夹，并在客户档案保存实际目录路径。打开新建表单、尚未确认的识别草稿或取消新建不触发建目录。此操作是正常新建客户流程的一部分，不要求用户每次再手动建目录。

FR-C17 识别系统实际桌面位置，兼容桌面重定向；不将开发机用户名或桌面路径硬编码为所有用户的目录。目录名合法化、全称或简称选择以及同名冲突方案在详细设计时确定。存在同名目录时核对客户归属，不擅自覆盖、删除或合并已有内容。

FR-C18 文件夹创建或路径关联失败时，界面明确显示失败及可重试状态，不虚报建档归档全部成功。重试应复用已核对的客户与目录，不产生重复客户和多份无关联目录；不得为回退而删除原先存在的客户目录。客户详情建议提供打开对应文件夹的入口。

## 7 项目台账与明细需求

### 7.1 项目与型号规格

FR-P01 新建项目时选择已建档客户，填写终端客户和项目基本信息；新客户先建档或形成待补全的客户草稿。

FR-P02 同一项目支持多条型号规格明细。每条明细独立记录材料型号、成品规格、报价、需求预测、预计量产时间和交易阶段。

FR-P03 项目列表支持展开或进入详情查看明细，不将同一项目的多个材料型号误算为多个独立项目。

FR-P04 同一客户的新项目建立新项目；同一项目的新订单进入原项目的订单历史。资料不足以确定项目归属时进入待确认状态。

### 7.2 原18列项目报告映射

| 原列 | 字段 | 建议归属与规则 |
| --- | --- | --- |
| A | 负责人 | 项目经办信息；明细存在差异时可覆盖，规则待确认 |
| B | 日期 | 保留原填报日期；导出使用建档日期还是最近跟进日期待确认 |
| C | 产品线 | 型号规格明细，支持项目级默认值 |
| D | 案子状况 | 结构化业务阶段，保留原1至7编码的兼容映射 |
| E | 客户 | 关联实际交易客户，导出客户名称 |
| F | 终端客户 | 最终使用整体产品的企业，允许与客户不同 |
| G | 项目名称 | 关联项目主档，不作为唯一识别键 |
| H | 应用 | 项目或明细的应用场景 |
| I | 材料型号 | 项目明细 |
| J | 成品规格 | 项目明细；同一型号不同规格分别跟进 |
| K | 单价 | 明细当前报价；与每笔订单成交单价分别保存 |
| L | 预估年用量 | 预测数据，保存数值及单位；不是实际订单累计数量 |
| M | 预估年营业额 | 预测数据；计算口径和单位换算规则待确认 |
| N | 项目状态 | 可读的当前业务说明，与结构化阶段配合 |
| O | 预估量产时间 | 支持日期、月份、季度及待定；保留原精度 |
| P | 竞争对手 | 项目明细相关信息 |
| Q | 竞争对手单价 | 独立于我方报价，保存相应单位口径 |
| R | 备注 | 最新摘要，完整历史另行保留 |

FR-P05 现有工具中的ODM集成商、模组厂、测试阶段需求数量、项目预计总需求量等信息继续保留，不因改用18列报告而丢失。ODM集成商、模组厂与实际交易客户的具体关系待确认，不能直接自动等同。

### 7.3 阶段和分组

FR-P06 主跟进项是业务交易阶段。根据原报告兼容报价、样品送测、新产品导入NPI、验证通过待量产、下单量产、验证失败结案、项目取消等状态；更细的询价、已报价、待下单等显示选项在详细设计时确认。

FR-P07 EVT（工程验证测试）、DVT（设计验证测试）、PVT（生产验证测试）作为测试阶段辅助字段，不替代业务交易阶段。MP（量产）、NPI（新产品导入）、EOL（生命周期结束）等缩写在界面中附中文说明。

FR-P08 报告分类与订单是否真实成交分开判断。样品单记入订单列表，但对应项目明细仍可处于开发状态；确认正式量产后相关明细默认归成交报告。

FR-P09 开发、成交、EOL为报告分类；重点项目作为独立标记。同一记录允许出现在所属分类页和重点项目页，应用统计不得因此重复计算项目或预测金额。

FR-P10 用户可手动调整分类并说明原因。AI不得仅凭“下单”“备料”等字样把开发项目直接判断为已量产。

## 8 业务跟进历史

FR-F01 项目和具体型号规格明细都可以新增跟进记录，至少包含日期、内容、关联对象和资料来源。

FR-F02 更新业务阶段、报价等关键字段时，保存变化前后值及关联跟进记录，以便理解最新状态的来源。具体自动留痕范围在设计时确定。

FR-F03 跟进历史按时间查看；新记录不覆盖旧沟通、旧报价或旧订单。修正误录内容要能区分发生时间与修改时间。

FR-F04 截图可以作为跟进来源关联到正确客户、项目和明细。是否长期保存原始截图、保存多久以及是否允许脱敏后保存待确认。

## 9 订单与订单明细

FR-O01 每笔真实采购独立建单。支持样品与量产用途；后续复购作为新订单，不覆盖上一笔。

FR-O02 订单至少关联实际交易客户，包含客户订单号或内部编号、下单日期、用途、备注及多条明细。外部订单号未知时不能虚构客户订单号。

FR-O03 每条明细关联对应的项目型号规格，记录本次数量、单位、成交单价、金额和约定交期。界面可从项目明细带出资料，提交前核对。

FR-O04 总金额由订单明细按明确的价格、数量、税费口径计算。正式订单价格以本次订单证据为依据，项目最近报价不能未经确认就视为成交价格。

FR-O05 同一订单跨多个项目是否存在尚未确认。建议订单属于客户，订单明细分别关联项目，以保留兼容空间。

FR-O06 交易和收款条件自动引用客户已约定条款，常规新建订单不重复向用户提问。正式变更交易条件的入口在客户档案中处理。

## 10 交货与收款

### 10.1 交货

FR-D01 默认提供整单交货的快捷操作，符合多数订单一次交完的习惯。

FR-D02 支持对同一订单多次交货，按明细记录每次交货日期和数量，显示应交、已交、未交数量。

FR-D03 不同型号规格的数量分别计算，单位不同的数量不能直接合并成一个总数量。多条明细的交货记录可归属同一交货批次。

FR-D04 超交、退货、换货、取消剩余数量等特殊情况尚未确认；基本交货流程不得通过修改订单原数量来隐藏历史交货事实。

### 10.2 收款

FR-R01 默认支持整单一次收清，并记录收款日期和实际金额，显示应收、已收、未收及收款状态。

FR-R02 收款时间以客户档案的约定为参考；实际是否收到货款由收款记录决定，不能因客户为预付款或月结就自动判定已收款。

FR-R03 支持手动录入收款事实。分次收款、同一次收款结清多张订单、账期起算和逾期判断口径尚未确认；不得把这些高级处理视为已确认需求。

FR-R04 银行流水连接、自动核销及完整财务凭证不在当前已确认范围。

## 11 截图识别与助手录入

### 11.1 已确定的建设顺序

第一阶段先使应用具备可靠的客户、项目、订单、跟进及草稿数据结构。用户在当前对话中发送聊天截图，由助手识别并通过应用录入。后续如接入应用内视觉模型API，继续使用相同的草稿、核对和保存规则。

### 11.2 识别和保存流程

1. 接收用户选择提供的截图或其他资料，按材料实际内容识别文本与上下文。
2. 分辨资料涉及客户建档、项目业务更新、报价、样品订单、量产订单、交货还是收款。
3. 查找可能关联的客户、项目及具体型号规格。只提供候选，不以名称相似直接覆盖记录。
4. 生成草稿，展示拟填写字段、原始依据、缺失项与冲突项。
5. 助手自检，核对主体、订单用途、数字、日期、型号、规格、单位、单价与金额关系。
6. 不确定字段留空，一次向用户询问一个问题；用户补充资料或手动补填。
7. 确认目标及重要字段后写入正式数据，并保留来源和操作记录。

### 11.3 具体要求

FR-A01 主要输入是聊天截图。多张连续截图、消息先后顺序、相对日期和聊天对象别名应在识别时关联理解；资料不足时提示不确定。

FR-A02 不得把“准备下单”“待报价后下单”“希望采购”等意向直接写成已经成交的订单；“已交货”“已付款”也需要来源支持。

FR-A03 截图中没有明确说明的终端客户、单价、税费、数量、付款条件等不自动猜测。不得通过过往客户样例补齐新客户资料。

FR-A04 识别需同时考虑项目、型号与规格；同一型号的不同规格不能误合并。重复提供同一截图或同一订单时应提示可能重复。

FR-A05 数字和金额优先展示可核对的来源片段，不用未经验证的AI置信度百分比代替用户判断。

FR-A06 当前对话的识别能力与本地应用内置AI是两种执行入口。未接入模型服务前，不能在应用中声称具备独立AI识图功能。

FR-A07 未来应用内识图需另行确定模型服务、API密钥、费用和外发资料范围。密钥放在后端配置，不进入前端或导出文件；不得未经明确选择将客户资料自动发送给外部服务。

## 12 导入导出与归档

### 12.1 项目报告

FR-X01 输出项目报告时沿用原18列业务结构，并提供开发、成交、EOL、重点项目四张工作表。

FR-X02 导出代表各型号规格明细的最新情况，不因同项目多笔采购而重复导出预测需求。重点项目页作为重点记录的另一种查看方式，不新增业务实体。

FR-X03 默认生成新的导出文件，避免直接覆盖原工作报告。自动更新指定原文件、保留旧文件还是覆盖方式需要另行确认。

FR-X04 支持现代`.xlsx`文件是设计建议。公司是否必须继续使用`.xls`、是否要求完全保持原表版式和公式，需要确认。不得仅改扩展名伪装格式。

### 12.2 导入

FR-X05 现有CSV导入是追加模式，不是模板配置或按项目自动更新。后续要增加预览、错误定位、重复候选及追加或更新确认。

FR-X06 新版导入应识别项目报告的18列，以及客户、项目、型号、规格之间的关系。不得仅凭项目名称去重，也不得把重点项目页中的同一业务记录再次导成新项目。

FR-X07 保留日期、月份、季度文本精度；不能正确识别的单元格列为待确认。源文件原值应可追溯。

FR-X08 导入前展示新建客户、新建项目、新建明细、更新和可能重复的数量。批量写入时避免只写入一半而无法恢复。

### 12.3 客户桌面归档

FR-X09 每个客户对应桌面上的客户文件夹，按FR-C16在软件新建客户成功时自动创建并绑定；后续备案表、资信资料及其他文件继续归入已关联目录，不在每次生成文档时另建一个同名客户文件夹。

FR-X10 客户文件夹命名需处理Windows非法字符及同名冲突；不能直接用聊天截图中的未经核对名称建成正式客户目录。

FR-X11 已生成备案表的模板版本、生成时间和补填状态应可查询。正式归档前核对客户主体和文件内容；重新生成时保留旧版或由用户明确选择替换。

FR-X12 若用户直接在Word文件中手动补填，应用与Word之间是否需要重新读取回写，必须在实现前确定，不能假装两处会自动同步。

### 12.4 备份与恢复

延续此前提出的自动备份、Excel导出及导入预览完善方向。建议备份包含数据库、客户附件、模板版本与必要关联信息；默认保留最近30份的方案仍需在存储和恢复设计中落定。

备份需要一致性快照，不能在不知道数据库是否处于写入状态时简单复制活动数据文件。恢复前应展示备份时间、范围及替换影响，并保留恢复前的可回退副本。

- 未来如开放局域网或多人访问，需另行设计身份验证、权限和数据隔离，不能沿用当前无账号的单机假设。
- AI接口关闭或未配置时，手动录入、助手操作和普通导入仍可使用。

## 15 分期建议与开发边界

### 阶段一 客户与项目基础

建立客户档案及长期交易条件，新建客户成功时自动建立并绑定桌面客户文件夹；完善项目和型号规格明细；业务阶段与测试阶段分开；建立跟进历史；支持重点标记和原18列报告映射。

### 阶段二 订单交货收款

建立独立订单及多项明细；样品与量产订单分别记录；支持整单交货、分批交货和一次收清；按客户条款展示后续交易信息。

### 阶段三 备案表和数据流转

实现空白客户备案模板填写、自检、空缺处理与桌面客户文件夹归档；完善Excel导出、导入预览、重复确认与备份恢复。阶段一开始时就应确定所需字段，避免到本阶段才重做数据结构。

### 阶段四 可选应用内AI

在用户确定服务和资料外发范围后，增加截图上传、视觉模型识别和来源核对入口，沿用前面阶段的草稿保存流程。

用户在阶段一至三即可向当前对话提供截图，由助手按已建成的应用能力识别并操作录入，不必等待应用内AI服务。

以上为功能拆分建议，不是已批准的最终排期。此前对自动备份、Excel导出和导入预览的时间估算不适用于本次扩展后的整套客户与订单管理范围；正式开发前需按确定范围重新估算。

| AC-13 | 填写客户Word备案表后逐项自检，不确定项留空；由用户补填后归档到正确桌面客户文件夹，原模板和旧文件保留。 |
| AC-14 | 已有客户样例的地址、电话、账号等不会出现在新客户的空白或自动填写文件里。 |
| AC-15 | 导出报告保留18列和4张表；已确认量产的明细与开发明细分别展示；样品订单不直接改变项目量产状态。 |
| AC-16 | 导入“2026年Q4”等量产预估时间保留季度精度；重点表同一业务记录不再次生成独立项目。 |
| AC-17 | 旧9字段项目数据完成迁移后可追溯；原有ODM、模组厂、测试数量等不会丢失。 |
| AC-18 | 备份恢复同时保持数据库与客户附件的关联；失败时可以回退，不产生只有记录没有文件的半恢复状态。 |
| AC-19 | 选用资信模板生成其他客户文件时，不继承模板遗留的法人、银行账号、经办人、良好评价或预选来源；未确认字段留空，原模板保留。 |
| AC-20 | 组织代码与营业执照号码文本不一致时提示核对；样例留空的财务、信用额度等字段仍标记为未知或适用性待确认，不自动当作免填或数值0。 |
| AC-21 | 在软件中成功新建一个客户，尚未生成任何Word时，桌面已出现对应客户文件夹，客户档案中关联的路径正确；取消新建不创建客户目录。 |
| AC-22 | 同一客户后续生成备案表或资信文件时使用原关联目录；重复提交或重试不创建重复客户与重复目录。 |
| AC-23 | 桌面目录无写入权限或发生同名归属冲突时显示明确问题；已有目录及文件保留，界面不显示文件夹创建成功。 |

## 17 待确认事项

这份清单用于后续一次询问一个问题。本次不要求用户一次性回答全部问题。

| 编号 | 待确认内容 | 对开发的影响 |
| --- | --- | --- |
| Q-01 | 不确定字段由用户在应用中补填还是直接编辑Word；若直接改Word，是否需要回读同步 | 决定草稿、正式数据及文档之间的一致性流程 |
| Q-02 | 资信模板已收到；是否需要全字段录入及自动生成、样例空白字段的正式免填规则 | 决定客户资信模块范围与字段校验 |
| Q-03 | 同一张订单是否可能包含不同项目的明细 | 决定订单行的项目关联及录入限制 |
| Q-04 | 是否存在分次收款或一笔款结清多张订单 | 决定收款与订单之间的分配关系 |
| Q-05 | 退款、退换货、取消订单或取消剩余数量是否进入首期 | 决定异常流程及金额数量回退 |
| Q-06 | 最终业务阶段选项及EOL判定；跨开发和量产的同项目如何汇总展示 | 决定状态字典、筛选和导出样例 |
| Q-07 | 价格含税口径、币种、数量单位、单位换算和金额舍入规则 | 决定报价、订单、预测与报表计算 |
| Q-08 | 报告日期的含义、预估年营业额计算口径及是否允许手工调整 | 决定18列报告的准确输出 |
| Q-09 | 项目名称未知或原表为“/”时，是否允许建立待补全项目 | 决定导入和截图信息不足时的保存规则 |
| Q-10 | ODM集成商、模组厂与客户、终端客户之间的归属 | 决定旧字段迁移与新表单布局 |
| Q-11 | Word最终输出格式`.doc`或`.docx`，是否必须完全保持公司原版式 | 决定模板转换、填写与版式验收方式 |
| Q-12 | 创建时点已确定为软件新建客户成功时；全称或简称、已有文件夹匹配及文件名版本规则待确认 | 决定目录命名和冲突处理，不影响自动建目录要求 |
| Q-13 | Excel输出`.xls`或`.xlsx`，导出新文件还是经确认更新指定原报告 | 决定兼容性和写入方式 |
| Q-14 | 截图原图的保存位置、保留时间和删除要求 | 决定附件与隐私管理 |
| Q-15 | 客户备案未补完时是否允许输出待补全草稿；审批和核准流程由谁完成 | 决定档案完成状态与文档输出规则 |
| Q-16 | 备份位置、周期、保留份数与恢复入口 | 决定本机备份的完整设计 |
| Q-17 | 应用内AI服务、API密钥、费用及资料外发范围 | 仅在可选应用内AI阶段开始前确认 |
| Q-18 | 资信模板遗留值清理、经办人配置、公司落款适用性及勾选/红字视觉核对 | 决定正式模板基线；不能直接继承当前模板预填内容 |
